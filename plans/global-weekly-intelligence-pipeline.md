# 全球周度情报流水线增强蓝图

> 目标：让 GatherInfo 在在线采集、多语种中文化、关键事实精编、业务分类和周度出版方面达到并逐步超过 InfoRoute；每个显式启用周刊且通过 readiness 预检的主题，每周稳定形成 2 份文档，每份 30–40 条独立、高质量、可溯源信息。候选不足时只报告缺口，不降低门槛凑数。

## 1. 基线与不可破坏约束

- 2026-08-04 数据基线：342 个来源、281 个标记启用、216 条信息、最近 7 天按 `published_at` 统计为 0、4 份报告。
- InfoRoute 对标基线：954 个来源画像、19,793 条历史信息、9 套结构化 Prompt；其强项是离线证据目录、来源合规画像和素材包，不是实时网络采集器。
- GatherInfo 当前优势：连接器注册表、受控并发、LLM 语义检索规划、严格发布日期窗口、中文质量审核、归档/分析双报告、MD/HTML/DOCX/PDF 导出。
- 当前测试锚点：`backend/.venv/bin/python -m pytest backend/tests -q` 为 439 passed；前端必须持续通过 `npm --prefix frontend run build`。
- 保持原始 URL、发布日期和原文快照；模型只做查询规划、翻译、精编和分类，不充当事实来源。
- 不绕过登录、验证码、付费墙、WAF、robots 或站点访问控制；来源未核验时不能自动升级采集权限。
- 兼容已有 `/reports/generate`、`/reports/batch-generate` 和历史 `Report` 数据。
- 现有用户修改文件不得被回退；发生重叠时基于当前工作树增量适配。

## 2. 成功指标

| 层级 | 指标 | 验收门槛 |
|---|---|---|
| 来源 | 可执行来源 | `is_active` 不再等同于可采集；100% 给出 readiness/compliance 原因 |
| 预检 | 可出版性 | 基于最近 14/30 天候选率、详情成功率、LLM 通过率计算；不达标只能预览缺口 |
| 发现 | 周候选池 | 每个周刊主题可配置 120–160 条候选审核预算，不受每源 9 条硬上限限制 |
| 正文 | 可独立阅读率 | 入库正式信息有可核验日期、原始 URL，中文整理稿不少于 180 字 |
| 多语种 | 中文化 | 非中文正式信息 100% 有中文标题、摘要、正文和原始语言记录 |
| 分类 | 结构化覆盖 | 正式信息包含业务分类、国家/地区、风险类型、产品/对象、涉华关联、优先级 |
| 精选 | 周刊产量 | 候选充足时稳定选出 60–80 条，拆成 2 份、每份 30–40 条 |
| 多样性 | 来源集中度 | 单一来源不超过单卷 20%，并记录分类/国家/语言/来源分布 |
| 幂等 | 重跑稳定性 | 同主题、同周、同卷重复请求返回同一完成结果，不重复出版 |
| 证据 | 可追溯性 | 每条刊载信息保留 item ID、URL、发布日期、来源、质量分和选择原因 |
| 质量 | 自动验证 | 新增逻辑单元/集成测试覆盖关键路径；后端与前端基线全部通过 |

## 3. 依赖图与并行边界

```text
S1 质量合同与评测基线
 └─> S2 来源画像/合规门禁/安全获取
      ├─> S3 候选扩容与正文补全 ─┐
      └─> S4 多语种结构化精编 ───┼─> S5 周刊精选/分卷/审计 ─> S6a API
                                  │                         ├─> S6b 调度
                                  │                         └─> S6c 前端
                                  └────────────────────────────> S7 基础多载体导出
                                                            └─> S8 真实运行评测
```

- S2 是 S3 详情抓取和 S4 全文 LLM 处理的硬前置；S3/S4 只能在门禁合同落地后并行。
- S5 依赖 S3 的候选量与 S4 的结构化元数据。
- S6/S7 依赖 S5 的稳定模型和幂等键。
- 每步独立可回滚；数据库新增字段全部 nullable 或带保守默认值。

## 4. 分步施工计划

### S1 — 冻结质量合同与对标评测

**上下文**：当前“采到多少”和“出版多少”没有一条可量化漏斗，导致 281 个启用来源仍可能 7 天零产出。

**任务**：

1. 增加只读质量审计，统计来源 readiness、候选、日期通过、正文通过、LLM 通过、去重入库、入选周刊的逐阶段转化率。
2. 增加 14/30 天出版可行性预检；未达到 `min_items` 的主题不能自动出版。
3. 固化 InfoRoute 的七类业务分类与 GatherInfo 现有类别映射。
4. 建立 20–40 条固定样本的中文整理、分类、去重和周刊选择回归集。

**验证**：审计命令不修改正式数据；同一数据库重复运行输出一致；样本评测可在无网络条件下运行。

**退出条件**：能回答每个主题为何不足 60 条，以及损失发生在哪一阶段。

**回滚**：删除只读审计模块和测试，不涉及 schema。

### S2 — 来源画像与合规门禁

**上下文**：InfoRoute 的核心优势是每个来源记录 discovery URL、语言、robots、条款、LLM 使用许可与原始来源追溯要求；GatherInfo 目前只有宽泛的 `legal_basis/compliance_note`。

**任务**：

1. 为 `SourceConfig` 增加 `verification_status`、`discovery_urls`、`robots_status`、`terms_status`、`llm_ingest_allowed`、`origin_resolution_required`、`crawl_delay_seconds`、`verified_at`。
2. 新建纯函数 `evaluate_collection_policy()`，返回允许/拒绝、理由、允许的内容深度（元数据/短摘录/全文）。
3. 将 InfoRoute 已核验的高价值官方来源画像以可审计 seed/import 方式迁移；不覆盖用户配置和密钥。
4. 在 connector 运行前执行门禁；旧来源采用兼容模式并标记 `legacy_unverified`，不可静默宣称已核验。
5. 新建 `safe_fetch_url()`：只允许 HTTP(S)；DNS 与每次重定向后拒绝 loopback/private/link-local/multicast；限制重定向次数、响应字节、HTML MIME、超时，并按 host/crawl delay 限速。

**验证**：允许/拒绝矩阵单测；未核验、LLM 禁止、访问拒绝来源不能进入自动全文 LLM；现有已配置搜索源保持可回滚兼容。

**退出条件**：所有活动来源均能解释“为什么可采/不可采、可处理到什么深度”。

**回滚**：关闭门禁 feature flag；保留 nullable 画像字段，不删除用户数据。

### S3 — 候选扩容、详情补全与日期核验

**上下文**：`SourceConfig.max_items_per_run` 已存在且当前生产值为网页 4、RSS 12、Tavily 12，但 `engine.py` 又在质量审核前统一截为 9；Tavily 日期核验已经下载详情页，却丢弃抽出的正文。

**任务**：

1. 第一小步移除统一 9 条硬截断，使用已有来源 `max_items_per_run` 与 160 条全局安全顶线；后续独立增加主题级 `candidate_review_budget`。
2. Tavily/RSS 候选在合规允许且摘要过短时补抓详情；复用 `extract_article_text()`，同时补正文、标题、摘要、发布日期。
3. 详情失败只记录原因并保留可审计 lead；不得伪造日期，不得绕过访问控制。
4. 对 URL、标题+正文指纹和同事件近重复分层去重，避免候选预算被转载耗尽。

**验证**：短摘要补全测试、日期优先级测试、普通来源保守限额测试、周刊主题 120+ 候选预算测试、访问失败降级测试。

**退出条件**：候选审核量由配置决定，搜索 lead 能在进入质量门前获得可独立阅读正文。

**回滚**：关闭详情补全；候选上限退回来源值，不恢复全局魔法数。

### S4 — 多语种结构化精编与证据字段

**上下文**：现有 LLM 已能输出中文标题/摘要/正文，但分类仅有粗粒度字符串，周刊无法按国家、风险、产品和涉华关系排版。

**任务**：

1. 将质量审核 JSON 合同扩展为：`business_category`、`risk_type`、`countries`、`products`、`actors`、`routes`、`china_relevance`、`priority`、`key_facts`、`evidence_claims`、`short_quote`、`publishability`；引用长度受来源 `content_depth` 限制。
2. Pydantic/纯函数校验模型输出；非法 JSON、缺证据、分数不足不得作为正式信息入库。
3. 保留原标题、原摘要、原文 hash、原语言、抓取时间、content depth 与许可范围；中文化内容另存，不把被截断快照宣称为完整原文。
4. 新增 `item_topic_memberships`，用 item/topic/run 多对多关系表达同一信息属于多个主题，周刊不得只依赖 `CollectedItem.topic_id`。
5. 增加非破坏性的历史条目批量补齐状态机；默认只写审核结果与缺口，不自动删除历史条目。

**验证**：多语言样本、单位换算链、禁止臆测、非法 schema、部分批次失败持久化、历史回填幂等测试。

**退出条件**：正式信息可按业务分类、国家、风险、产品、涉华关系和优先级检索/组稿。

**回滚**：读取端回退到旧 `translation_zh/quality_review`；保留新增 metadata 以便审计。

### S5 — 周刊精选、双卷编排与审计

**上下文**：现有报告按时间排序，缺少 80 条精选、两卷拆分、幂等键和选择审计。

**任务**：

1. 新建 `weekly_report_engine.py`，输入主题、周窗口、目标 80、每卷 40、最低每卷 30。
2. 过滤无日期/空正文/低质量候选；按规范 URL/content hash 去重。
3. 使用透明分数（质量、相关性、时效、权威性）与多样性惩罚（来源、国家、分类、语言）选择 60–80 条。
4. 使用 `Report.series_id/period_key/part_index/part_total/selection_policy/selection_audit/retry_count/last_error_at`；事务内 get-or-create，唯一冲突后读取既有卷，避免并发重复出版。
5. 每卷保留独立条目，不跨条目合并事实；候选不足时明确记录缺口，不用低质量信息凑数。

**验证**：80→40+40、65→33+32、少于 60 拒绝/预览、来源集中度、去重、排序确定性、重复请求幂等、部分失败重试。

**退出条件**：同一主题同一周稳定得到 2 份不重叠、每份 30–40 条的周度文档记录。

**回滚**：停用周刊 API/调度；旧报告模型继续工作，新增字段不影响历史数据。

### S6 — API、调度与可操作前端（拆为 3 个独立变更）

**上下文**：当前自动报告每次采集只生成一份；全局 schedule 还引用了模型不存在的 `timezone` 字段。

**任务**：

1. S6a：新增 `POST /api/v1/reports/weekly-generate`、预览、系列详情和失败卷重试接口。
2. S6b：APScheduler 注册独立周刊作业；`week_window_for_beijing()` 定义周一 00:00 到下周一 00:00，查询边界转 UTC，`period_key=YYYY-Www`。
3. S6c：报告页增加“周度合集”模式，显示候选/入选/淘汰、两卷状态、分布与下载；不破坏单报告流程。

**验证**：API 集成测试、调度幂等测试、前端 build、关键交互和错误/空状态测试。

**退出条件**：用户可在 UI 配置、预览、生成、重试并下载周刊两卷。

**回滚**：关闭周刊配置；保留手动 API 和已生成文档。

### S7 — 出版级多载体排版

**上下文**：现有 DOCX 只是逐行转标题/段落，且默认文件名格式可能忽略 `Report.title`，两卷存在覆盖风险。

**任务**：

1. 修复文件命名唯一性，确保同主题同日两卷不覆盖。
2. 第一版让 Markdown/HTML/DOCX 共享条目口径与中文字体、分类分隔和来源链接；高级目录、页眉页脚与页码留到真实使用反馈后。
3. 输出周刊索引 manifest，列出系列、两卷文件、条目 ID、hash 和生成时间。

**验证**：读取生成 DOCX/PDF 确认 60–80 个标题与链接均存在；两卷文件路径不同；manifest hash 可复算。

**退出条件**：每周可交付两份可阅读、可审计、格式一致的正式载体。

**回滚**：保留 Markdown 兜底；单格式失败不得阻塞其他格式。

### S8 — 真实运行评测与逐步放量

**上下文**：当前最近 7 天为零，代码通过不等于周产量达标。

**任务**：

1. 先选择 1 个主题、10–20 个已核验来源运行 2 周 canary，再扩展主题和地区。
2. 每日检查采集漏斗、日期缺失、翻译失败、来源集中度、LLM 通过率和出版缺口。
3. 把误收/漏收反馈转成固定评测样本和分类规则；模型/Prompt 版本写入审计。
4. 达到 60–80 条/周后再扩展并发、候选预算和来源数量。

**验证**：连续两周每周两卷、每卷 30–40 条；人工抽检事实准确率与中文可读性达到验收阈值；无来源合规越界。

**退出条件**：真实数据连续两周满足产量、质量、多样性和可追溯性目标。

**回滚**：按主题停用自动出版/来源，不删除历史报告、条目或审计记录。

## 5. 对抗性审查清单

- 是否把“来源标记启用”误当成“来源可执行”？
- 是否用 LLM 生成了不存在的来源、日期、金额、主体或结论？
- 是否为凑满 80 条放宽了发布日期或质量门槛？
- 是否让单一搜索引擎、国家或来源占据大多数版面？
- 同主题同周重跑是否会重复记录或覆盖卷文件？
- 详情抓取是否绕过了访问控制或忽略来源内容使用边界？
- 非中文信息是否同时保留原始语言和中文整理稿？
- 选择与淘汰是否可解释到具体 item？
- 可选导出依赖失败时，Markdown 是否仍可用？
- 测试是否污染正式 SQLite 数据库？

## 6. 计划变更协议

- 新证据只允许调整尚未开始的步骤；已完成步骤若需返工，新增修订记录而不改写历史结论。
- 任何 schema 扩展先写兼容迁移与回滚策略，再修改运行代码。
- 若真实 canary 证明候选量不足，优先补来源/正文/日期，不降低质量门槛。
- 若 LLM 成本或延迟超限，先批处理、缓存与缩短候选上下文，不取消证据校验。
- 每完成一步，更新本文件状态、测试结果和真实数据指标，并同步更新 `AGENTS.md`。

## 7. 本轮实施范围

本轮先完成 S1/S2 的最小硬前置（readiness 合同、来源处理权限、安全 URL 获取），再完成 S3 的候选限额/受控详情补全、S4 的结构化精编合同，以及 S5 的周刊编排最小闭环。前端 dirty 文件仅在后端合同稳定且无冲突时增量接入。已完成的 Report 周刊字段、Schedule timezone、来源预算改造在后续步骤中只做接线和验证，不重复迁移。
